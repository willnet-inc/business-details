# Ruby / Rails開発を継続的に支える技術顧問サービス

株式会社ウィルネットは、Ruby / Railsを使う開発チームに継続的に参加し、技術的な意思決定と開発の改善を支援しています。

「この設計で進めてよいのか」「技術的負債をどこから解消すべきか」「Railsの更新が止まっている」といった課題について、コードや事業の状況を理解したうえで、一緒に対応を考えます。相談への回答に加えて、課題の調査、改善提案、実装・レビューまで関わります。

担当するのは、株式会社ウィルネット代表の [@willnet](https://github.com/willnet) です。2016年1月から技術顧問として、各社のRails開発を支援しています。

## こんな課題をお持ちのチームへ

- 設計や技術選定について、社内の事情を理解した相手に相談したい
- 技術的負債が増えてきたが、何から手をつけるべきか判断しづらい
- Ruby / Railsやgemのアップデートが滞っている
- テストやCIに不安があり、変更やリリースに時間がかかる
- 不具合への対処を繰り返しており、原因を掘り下げて改善したい
- 特定のエンジニアに知識や判断が集中している
- 新しくRailsを採用するため、設計や開発の進め方を相談したい

Ruby / Railsを利用している、またはこれから利用する会社を主な対象としています。それ以外の技術についても相談いただけますが、内容によっては、より適した専門家への相談をお勧めすることがあります。

## 支援を通じて目指すこと

チームが、日々の開発を進めながら、必要な改善にも取り組める状態を目指します。

- **判断の理由を説明できること**
  選択肢とその利点・欠点を整理し、自社の事情に合った技術判断ができる。
- **改善の優先順位が見えていること**
  技術的な課題と影響を把握し、事業上の優先順位も踏まえて対応を進められる。
- **安心して変更を重ねられること**
  テストやレビュー、継続的なアップデートを通じて、変更に伴う不安を減らせる。
- **知識や判断の背景がチームに残ること**
  調査や改善の過程を共有し、同じような課題にチームで対応できるようになる。

## 具体的な支援内容

以下から、チームの課題と契約時間に合わせて取り組む内容を相談します。

### 技術的な意思決定の支援

Slackやオンラインミーティングで、設計、技術選定、実装方針などを相談できます。

一般的な選択肢を説明するだけでなく、既存のコード、運用体制、今後の開発予定などを踏まえて、何を選ぶかを一緒に考えます。

たとえば、次のような相談に対応します。

- 今後の機能追加を考えたとき、このテーブル設計で問題ないか
- このgemを採用してよいか。保守状況や既存システムとの相性も含めて検討したい
- この処理を同期処理のままにするか、バックグラウンドジョブに移すか
- Railsのアップグレードと機能開発を、どのような順序で進めるべきか
- この技術的負債は今解消すべきか。対応を後にする場合、何に気をつけるべきか

AIの回答や提案したコードについて、妥当性や自社への適用に迷った場合も相談できます。

### 開発状況の把握と課題の発見

継続的にコードや開発状況に触れ、気づいた課題を共有します。相談された内容に加えて、今後問題になりそうな点や、改善すると開発を進めやすくなる点も一緒に探します。

プロジェクト診断では、ソースコードや設定を確認し、たとえば次のような観点から課題を整理します。

- Ruby / Railsやgemのバージョン、更新を妨げている要因
- アプリケーションの設計や責務の分け方
- DBへのアクセスやバックグラウンドジョブの使い方
- テスト、CI、各種設定の状態
- 特定の箇所に変更や不具合が集中していないか

見つかった課題は、影響や対応の負担を踏まえて整理し、何から取り組むかを相談します。

### アップグレード・実装・レビュー

調査や提案に加えて、実際にコードを変更するところまで支援します。

主な例は、Ruby / Railsやgemのバージョンアップ、`config.load_defaults`の更新、既存コードの改善、個別のPull Requestのレビューです。

変更による影響を確認しながら、継続的にアップデートしやすい状態を整えます。

稼働は最大でも週1日程度のため、納期が近い機能の実装には対応できません。まとまった開発工数を必要とする作業については、社内のエンジニアと役割を分担しながら進めます。

### 不具合の調査とOSSへのフィードバック

アプリケーションの不具合について、原因の調査と修正を行います。

必要に応じてRailsやgemのソースコード、Issue、Pull Requestまで確認し、アプリケーション側の問題なのか、ライブラリの仕様や不具合によるものなのかを調べます。

Railsやgemに原因がある場合は、調査内容をIssueやPull Requestとして本体にフィードバックするようにしています。また、メンテナンスが滞っているgemについて、修正の取り込みやリリースに向けてメンテナに働きかけることもあります。

### 開発環境・プロセスの改善

安心して変更を重ねられるよう、テストやCI、レビューの進め方を見直します。

- 不足しているテストや、不安定なテストの改善
- CIの実行時間や失敗原因の調査・改善
- レビューで確認する観点やコーディングルールの整理
- 依存ライブラリを継続的に更新するための運用づくり
- 開発手順や設計の背景を共有するドキュメントの整備

AIの活用についても、チームの関心や利用状況に応じて、実務の中で小さく試し、効果や課題を一緒に確認します。

### 実務につながる学習と知識共有

チームの課題や経験に合わせて、ペアプログラミング、モブプログラミング、読書会、勉強会などを行います。

実際のコードや調査を題材に、どう考えて設計するか、何を手がかりに不具合を調べるか、変更の影響をどう確認するかを共有します。

たとえば、次のような進め方があります。

- 自社で発生したActive Recordの問題を題材に、挙動や設計を理解する
- Railsのアップグレードを進めながら、変更点や内部の仕組みを確認する
- レビューで繰り返し話題になる内容を、勉強会で整理する
- Ruby / Railsに不慣れなメンバーに向けて、読書会で基礎を学ぶ

読書会は原則として予習不要の形式で行い、題材や目的に応じて進め方を調整します。Ruby / Rails関連のニュース共有や、特定のテーマについてのソースコードリーディングも行っています。

### コミュニティ活動・発信の支援

Ruby / Railsのコミュニティ活動やOSS活動に関心があるメンバーを支援します。

[@willnetが主宰するginza.rb](https://ginzarb.github.io/)をはじめ、勉強会やカンファレンスの情報共有、プロポーザルの作成支援、社内イベントへの協力、テックブログへの寄稿などを行っています。

## 継続的に関わる理由

技術的な判断には、コードだけでなく、その設計になった経緯、プロダクトの方向性、チームの経験、運用上の制約などが関わります。

そのため、GitHubやSlackなどを通じて開発状況を把握し、定期的に調査やレビュー、改善に取り組む時間を確保する形をお勧めしています。

継続的に関わることで、毎回前提から説明する負担を減らし、過去の判断や現在の状況を踏まえた相談ができるようになります。

## 契約形態・連絡方法

週1日・8時間程度の稼働を確保する形をお勧めしています。

特定の曜日に8時間、または4時間の枠を確保する形が一般的です。確保した時間は、相談、調査、実装、レビュー、知識共有などに、課題の優先順位に応じて使います。

確保した時間以外でもSlackで質問を受け付け、おおよそ1営業日以内の返信を心がけています。

基本的にフルリモートで対応しています。東京近郊での出社は応相談です。

質問があったときだけ稼働する契約形態も相談可能ですが、会社やコードベースへの理解を深めるため、継続的に関わる形をお勧めしています。

## 専門外のこと

エンジニア組織づくりそのものを主目的とした支援は専門外です。開発現場で感じたことや、これまでの経験に基づく意見を共有することは可能です。

## お問い合わせ

[株式会社ウィルネットの会社ページ](https://willnet.jp/)にあるお問い合わせフォームからご連絡ください。

「まだ依頼するか決まっていない」「課題をうまく整理できていない」という段階での相談も歓迎しています。現在困っていることや、開発チームの状況をお聞かせください。
